## What we now have (text-extracted via Graph; still need actual .docx binaries — see Gaps)

### 1. Master blank template — `GE/7EA/Cover Page/7EA Borescope Cover Page 111825.docx` (current as of 2025-11-18)
This is the actual authoring template, not just a cover page — it contains the full report shell:
- Placeholder conventions: literal `X` for numbers/counts/positions, `Choose an item.` for Word content-control dropdowns (inspection type, TIL full/limited/none, unit-rotated yes/no, etc.), `XX`/`XXX` for measurements, `20XX` for prior-inspection years.
- Fixed section order matches the Report Composition standards doc exactly: Documentation & Photographs → Purpose → (Notes, delete-if-unused) → Overall Assessment → Inspection Details → Inspection Areas → Applicable TIL's → Inspection Access → Significant Observations and Recommendations → Observations (per-section tables) → Photos (per-section photo blocks).
- **Significant Observations and Recommendations is a pre-written library**, not free text: ~25 numbered boilerplate recommendation paragraphs covering the recurring 7EA findings (IGV rubs, bushing migration, impact damage, R-1 erosion, rolled metal/tip grinding on various stages, shim protrusion at 3 severity tiers, clashing damage, R-17 axial movement at 4 severity tiers, liner coating bulging, TP cracks, missing flex seal). Each has an inline usage note (e.g. "REMOVE FOR CALPINE, PSM and DUKE", "USE WHEN ET IS PERFORMED" vs "NOT PERFORMED", "WHEN MOLDS ARE NOT DONE") — i.e. conditional-inclusion logic keyed on customer and on which other services were performed, confirming Brett's "delete all that are not applicable" instruction from the formatting PDF.
- Observations tables are keyed by stage/component (R1...R17, S1...S17, EGV1/EGV2 for compressor; Position 1-10 × {Outer Mount Brackets, Outer Zipper Weld, Inner Zipper Weld, Inner Mount Bracket, Bull Horn Bracket} for combustion cold side; Position 1-10 × {Combustion Cap, Fuel Nozzles, Crossfire Tubes, Combustion Liner, Transition Piece} for hot side; Stage 1-3 × {Nozzles, Buckets, Shroud Blocks/Honeycomb Shroud} for turbine) plus a fixed "Percent of Component Inspected" column/field per Brett's rules (0% center-justified if not inspected).
- Photo blocks repeat a fixed field set per photo: `Component` / `Location` / `Observation` / `Comments`, two photos per page (matches "do everything in pairs" from the meeting and the Photo Section formatting rule).
- There's a separate **with-Generator** variant template: `7EA Borescope with Generator Cover Page 111825.docx`.

## Docx structural findings (from the actual binaries, added 2026-09-16)

Adam downloaded the real `.docx` files for the master template and the full sample report into this `reference/` folder (browser-pane download couldn't reach the local filesystem — manual download was the working path). Unzipped and inspected the raw OOXML directly:

- **Fonts confirm the standards doc exactly.** `styles.xml` docDefaults set `Times New Roman` document-wide; `Normal` style is `sz=24` (12pt, half-points); `Heading1` is `sz=28` (14pt, bold, centered); `Heading2` is bold/centered, size inherited from Normal (12pt).
- **Table widths confirm the "7 inch" rule exactly.** `w:tblW w:w="10080"` (10080 dxa = 7.0 in @ 1440 dxa/in) appears 33 times in the template, on essentially every section/observations table. A second recurring width, 10654 dxa (~7.4"), plus a 4375 dxa (~3.0") width belong to the two-column photo-grid tables.
- **Scope selection is a real Word content control, not a convention.** The "Inspection Type" field is a `<w:sdt>` with `<w:dropDownList>` containing exactly: `Borescope Inspection`, `Compressor Borescope Inspection`, `Combustion Borescope Inspection`, `Turbine Borescope Inspection` (plus placeholder `Choose an item.`). This is the actual mechanism, at the document level, for the "inspection scope" concept from the meeting — 41 `<w:sdt>` / 42 `w:dropDownList` content controls total in the master template (Type of Fuel, Site Contact, Unit Rotated yes/no, TIL Full/Limited/None per TIL row, Inspection Access Provided per combustion position, etc.), each following the same shape: `w:sdtPr` (id, placeholder docPart, `w:showingPlcHdr`, the `w:dropDownList` with `w:listItem` value/displayText pairs) → `w:sdtContent` (a table cell or paragraph whose text is the `PlaceholderText`-styled "Choose an item." until filled). To fill one programmatically: remove `<w:showingPlcHdr/>`, replace the content run's text with one of the listed `displayText` values, and (cosmetically) drop the `PlaceholderText` character style/red color.
  - **Tech implication:** this is well beyond what `python-docx` or JS `docx`/`docxtemplater` handle out of the box (none read/write content-control dropdowns natively). Direct OOXML manipulation (unzip → edit `word/document.xml` with a real XML library, matching the docx skill's own "editing existing documents" approach) is the right tool, in whichever language we end up building in.
  - There are also 132 `w:fldChar` field codes in the template (172 in the filled sample) — almost certainly the auto-updating date/page-number/TOC fields Brett described ("date will automatically update once the cover page is filled out"); haven't traced which specific fields yet.
- **The completed sample report keeps a handful of unresolved content controls** (17 `<w:sdt>`, 2 still showing a live `dropDownList` — likely Unit Rotated and one Inspection-Access-Provided cell) rather than stripping them after filling, and drops to 15 tables at the 7" width (fewer stage-position tables than the master, consistent with a single-scope report needing fewer Observations tables than the "all stages, all positions" master shell).
- **Media**: the blank master template ships with 34 embedded images — these are Brett's built-in instructional photos ("a couple of photos in there just for the newer guys, for photo orientation"), not real inspection content. The filled sample report has 237 media entries (mix of real photos plus `hdphoto*.wdp` — Word's WDP/JPEG-XR thumbnail sidecars, an artifact of how the photos were pasted in, not something we need to reproduce).

## Raw MDI output — received and inspected (2026-09-16)

Adam got an actual raw borescope-generated file from Brett: `7EA_Full_022825-Batavia.docx`, saved to `reference/raw-mdi-samples/`. This closes the last hard gap from Phase 1. Findings from unzipping it:

- **Structurally much simpler than the ATS template**: no `customXml`, no `docProps`, no `numbering.xml`/`fontTable.xml`/`theme`/`glossary`, and critically **zero content controls** (`<w:sdt>` count is 0) — this file is pure static tables/paragraphs/images, no dropdowns, no scope logic. All of that lives only on the ATS-template side; the raw MDI output is just data.
- **Header metadata table** at the top: a 2-column label/value table (`Menu Directed` / `7EA_Full_022825`, `Serial Number` / `Batavia`, `Date` / `11/12/2025`, ...) in Verdana. "Menu Directed" confirms the MDI ("Menu Directed/Driven Inspection") naming directly.
- **Every photo is a self-contained 3-part unit, repeated 178 times** (matches the number of individual observations/photos in this inspection):
  1. A filename caption line, auto-generated by the borescope software from the inspector's own MDI menu selections, e.g. `Stage_1_Rotor_Blade_Leading_Edge_Pressure_Side_001.JPG` — literally `{Component}_{Location}_{sequence}.JPG` with underscores for spaces. This is the exact line Adam said inspectors delete before pasting into the template.
  2. The photo itself (`<w:drawing>`; 261 total drawings in the package vs 178 captioned units — the gap is paired/uncaptioned second photos and one logo image).
  3. **A caption table with the exact same 4 fields as the ATS template's photo blocks**: `Component` / `Location` / `Observation` / `Comments` (e.g. `Stage 1 Rotor Blade` / `Leading Edge Pressure Side` / `Typical` / *(blank — Comments is filled in manually later, matching the sample report's ad hoc "Previously Identified" comments)*). Font is Verdana size 20 (10pt) — matches the Report Composition standards doc's Photo Section rule exactly.
  4. This caption table's width (4375 dxa / ~3.0") and the paired two-column layout width (10654 dxa / ~7.4") **are the identical numbers found in the ATS master template's photo-grid tables** — strong evidence the "paste into the template" step Adam described really is copying these table blocks near-verbatim, not re-authoring them.
- **A large separate "Inspection Points" / "Approved Inspection Points" table** also appears (not yet fully mapped) — likely the borescope's own record of which menu points were configured vs. actually visited during the inspection; worth reading in full once we're building the assembly parser.
- Still only have this one raw sample, from one MDI software version. The second version (Brett mentioned two) hasn't been provided yet — not a hard blocker for prototyping now that we understand the structure, but worth getting eventually to confirm the parser handles both.

**Practical implication for Phase 2/3**: the photo-assembly transformation looks mechanical and well-defined — for each of the 178 units in the raw file: drop the filename-caption paragraph, keep the drawing + its Component/Location/Observation/Comments table, and insert into the matching section of the ATS template (matching on the `Component`/`Location` text, which also cross-validates against the filename). This is very promising for a deterministic (non-AI) first pass, consistent with how the INA app's own deterministic parsers work.
